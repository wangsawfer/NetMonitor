## 1. 项目简介

NetMonitor 监控**指定应用程序及其全部子进程**发出的 DNS 查询，并以高刷新率实时显示。
它与"抓整机流量"的工具不同：你给出一个可执行文件路径，工具先启动监控、**再**启动该程序，
因此从目标进程的第一条 DNS 查询起就不会有真空期。

设计上有三个要点：

- **事件驱动**。捕获线程阻塞等待内核事件（ETW 回调、`pcap_next_ex`），
  没有任何定时轮询。数据流动时界面立即重绘。
- **进程归属准确**。主数据源是 ETW `Microsoft-Windows-DNS-Client` 提供程序的
  3006/3008 事件，它们由**发起查询的进程**写入，事件头里的 PID 就是应用程序本身，
  而不是转发查询的 `svchost.exe`。
- **界面与捕获解耦**。捕获线程只做最少的解析后入队；进程归属、去重、
  IP↔域名缓存、渲染全部在其它线程完成。界面即使卡住也不会丢包。

## 2. 功能概述

| 能力 | 说明 |
|---|---|
| 目标指定 | 命令行 `--app <路径>`（**可重复**，同时监控多个程序）；图形界面内「浏览…」+「添加」加入可执行文件，「按名称监视」+「添加名称」把映像名加入同一列表；`--attach <映像名>` 附加到已运行进程（可重复，收编该映像名的**全部**进程，浏览器必须用这个，见 §6.3） |
| 启动顺序 | 先建监控、后启动目标，确保无真空期 |
| 子进程覆盖 | 自动识别目标派生的全部子进程（浏览器这类多进程程序是主要用例） |
| 实时列表 | 每条记录含：时间戳、进程名、PID、查询类型、来源、域名、附加信息 |
| 主事件源 | ETW `Microsoft-Windows-DNS-Client`（事件 3006 / 3008） |
| 辅助抓包 | Npcap 捕获 UDP/53，补充自带解析器的应用；TCP 端口表做 PID 归属 |
| DoH/DoT 补充 | 从 443 / 853 的 TLS ClientHello 提取 SNI |
| 关联分析 | DNS 应答 → `IP ↔ 域名` 缓存；域名 → 最近解析进程的反向关联 |
| 交互界面 | 图形界面（`run-netmon-gui.cmd`）；无界面模式逐行输出，供脚本与自动化使用 |
| 界面功能 | 开始/停止、暂停/恢复滚动、清空、过滤、导出、统计、诊断日志、帮助 |
| 导出 | CSV 与 JSON，仅导出当前过滤结果 |
| 只显示目标进程 | 其它进程的事件在管线中被剔除并计数，不占用列表 |

## 4. 安装步骤

### 4.1 一键安装（推荐）

以**管理员**身份打开 PowerShell：

```powershell
cd D:\pythonProject\ipv6
powershell -ExecutionPolicy Bypass -File scripts\install.ps1
```

脚本会依次完成：

1. 安装 Rust 工具链到 `<项目>\.toolchain\`（`RUSTUP_HOME` / `CARGO_HOME` 都指到那里）；
2. 检测 MSVC C++ 工具集（只检测，不静默安装）；
3. 下载并解压 Npcap SDK 到 `<项目>\.cache\deps\npcap-sdk\`；
4. 静默安装 Npcap 驱动。

所有下载都缓存在 `<项目>\.cache\dl\`，重复执行很快，失败后可直接重跑。

可选参数：

```powershell
-SkipRust            # 已装好 Rust 时跳过
-SkipNpcapRuntime    # 只取 SDK，不装驱动
-NpcapVersion 1.79   # 指定 Npcap 版本
```

### 4.2 关于 Npcap 的安装位置

**内核驱动必须位于 `%SystemRoot%\System32\drivers\npcap.sys`。**
这是 Windows 的加载机制决定的，不是安装器的选择——驱动不在系统目录就无法被内核加载。
Npcap 官方安装器同样不提供"改安装目录"的开关；传入 `/D=<路径>` 会被忽略并让安装器以
退出码 2 失败（本项目实测确认，脚本中已注释说明）。

实际落盘情况：

| 内容 | 位置 | 大小 |
|---|---|---|
| 内核驱动 `npcap.sys` | `C:\Windows\System32\drivers\` | ~72 KB |
| 用户态 `wpcap.dll` / `Packet.dll` | `C:\Windows\System32\`（WinPcap 兼容模式） | ~600 KB |
| 安装器副本、SDK、全部缓存 | **项目盘（D:）** | 见 §12 |

也就是说，Npcap 在 C 盘上占用约 **1.6 MB**，且不可迁移；其余所有内容都在非 C 盘。

### 4.3 手动安装 Npcap

```cmd
npcap-1.79.exe /S /winpcap_mode=yes /loopback_support=yes /dot11_support=yes
```

- `/S` 静默安装
- `/winpcap_mode=yes` 把 `wpcap.dll` 放进 `System32`，第三方程序无需改 PATH 即可加载
- 验证：`sc query npcap` 应显示 `STATE : 4 RUNNING`

### 4.4 发布包

**单文件版** `NetMonitor-1.1.0-portable.exe`（推荐）：双击运行，不需要 Python，
也没有 `.cmd` 启动器。首次启动如果检测不到 Npcap，会询问是否用内置的安装程序
安装（需要管理员权限）。

**便携文件夹版** `NetMonitor-1.1.0-win64.zip` 解压后：

```cmd
install-npcap.cmd      :: 安装驱动（会自动请求管理员）
run-netmon-gui.cmd     :: 图形界面（需要 Python 3，会自动请求管理员）
run-netmon.cmd         :: 无界面，逐行输出（会自动请求管理员）
```

`deps\` 目录中已附带 Npcap 安装程序，无需联网。两种版本都需要 Npcap：引擎在
加载时链接 `wpcap.dll`，缺少它无法启动。

## 5. 构建步骤

```powershell
cd D:\pythonProject\ipv6
powershell -ExecutionPolicy Bypass -File scripts\build.ps1
```

流程：设置环境变量 → 跑单元测试 → 编译 release。产物在
`.cache\target\release\`（`netmon.exe`、`testapp.exe`、`etwprobe.exe`）。

参数：

```powershell
-Configuration debug   # 编译 debug 版
-SkipTests             # 跳过测试
```

若手工构建，需要保证：

```powershell
$env:RUSTUP_HOME      = "D:\pythonProject\ipv6\.toolchain\rustup"
$env:CARGO_HOME       = "D:\pythonProject\ipv6\.toolchain\cargo"
$env:CARGO_TARGET_DIR = "D:\pythonProject\ipv6\.cache\target"
$env:NETMON_NPCAP_SDK = "D:\pythonProject\ipv6\.cache\deps\npcap-sdk"
cargo build --release
```

`netmon\.cargo\config.toml` 中有两项配置，都带有详细注释：

- `LIBPCAP_VER = "1.9.1"` —— 告诉 `pcap` crate 按哪个 libpcap 版本编译。
  Npcap 的运行库与 libpcap 1.9.1 API 兼容，声明该版本才能启用
  `immediate_mode`、`buffer_size` 等现代接口。
- `target.x86_64-pc-windows-msvc.rustflags = ["-C", "target-feature=+crt-static"]`
  —— 静态链接 MSVC 运行库。否则产物会依赖 `VCRUNTIME140.dll`，
  在没装 VC++ Redistributable 的干净系统上无法启动。

`netmon\build.rs` 负责找到 `wpcap.lib`（Npcap SDK 的导入库）。
查找顺序：`NETMON_NPCAP_SDK` 环境变量 → `<项目>\.cache\deps\npcap-sdk` →
`C:\Program Files\Npcap\SDK`。

## 6. 运行方法

### 6.1 命令行参数

```
netmon.exe [OPTIONS]
```

| 参数 | 说明 |
|---|---|
| `-a, --app <PATH>` | 目标程序路径。**先启动监控，再启动它**。可重复：多个目标都是同一棵进程树的根 |
| `--arg <ARG>` | 传给目标的参数，可重复。所有 `--app` 共用同一组参数 |
| `--attach <IMAGE>` | 附加到已运行的进程（按映像名，如 `chrome.exe`），不启动新进程。可重复 |
| `--keep-alive` | 目标退出后继续监控，直到手动停止（浏览器等单实例程序必需） |
| `--watch <IMAGE>` | 持续按映像名识别进程，命中即收编（含其全部子进程）。可重复 |
| `--aaaa-workers <N>` | AAAA 查询工作线程数，默认 4；**0 表示关闭**该功能 |
| `--aaaa-bypass-cache` | AAAA 查询绕过解析器缓存（默认不绕过） |
| `--export-domains <PATH>` | 会话结束时导出**每个进程的域名表 + AAAA 结果**（`.json` 走 JSON） |
| `--hosts-file <PATH>` | 要管理的 hosts 文件，默认为系统路径 |
| `--hosts-backup-dir <DIR>` | 备份目录，默认在**可执行文件旁**的 `hosts-backups`（尽量不占 C 盘） |
| `--data-dir <DIR>` | 本地缓存目录（域名表快照 + hosts 更改记录），默认在**可执行文件旁**的 `netmon-data` |
| `--no-cache` | 不读也不写本地缓存：启动时域名表为空，也不留更改记录 |
| `--no-aaaa <MODE>` | 无 IPv6 的域名怎么处理：`block`（默认，指向 127.0.0.1）或 `skip`（不写入） |
| `--no-etw` | 关闭 ETW 主数据源 |
| `--no-npcap` | 关闭 Npcap 抓包 |
| `--loopback` | 同时抓取回环接口 |
| `--pcap-filter <EXPR>` | 覆盖内置 BPF 过滤器（诊断用） |
| `--session-name <NAME>` | ETW 会话名。默认按进程号生成，因此可多开 |
| `--headless` | 兼容保留：本版本没有终端界面，每次运行都是无界面模式 |
| `--duration <SECS>` | 无界面模式下运行指定秒数后自动退出 |
| `--show-responses` | 无界面模式下同时输出 DNS 应答行 |
| `--show-unattributed` | 输出无法确定属主的行（默认关闭，见 §11.2） |
| `--export <PATH>` | 会话结束时导出；扩展名 `.json` 走 JSON，否则 CSV |
| `--child-console` | 允许目标程序写入本控制台（`--stream-json` 下默认禁止） |
| `--doctor` | 打印环境诊断后退出 |

### 6.2 典型用法

```cmd
:: 无界面模式，监控浏览器（要窗口请用 run-netmon-gui.cmd）
netmon.exe --app "C:\Program Files\Google\Chrome\Application\chrome.exe"

:: 同时监控多个程序：每个都是同一棵进程树的一个根
netmon.exe --app "C:\App\main.exe" --app "C:\Tools\updater.exe"

:: 带参数启动（参数对上面每个 --app 都生效）
netmon.exe --app "C:\Tools\app.exe" --arg --profile --arg nightly

:: 附加到已经在跑的进程
netmon.exe --attach chrome.exe --keep-alive

:: 跑 30 秒并导出
netmon.exe --app "D:\app.exe" --duration 30 --export out.csv

:: 环境自检
netmon.exe --doctor
```

### 6.3 监控浏览器（Edge / Chrome）—— 必须先看这一节

浏览器是**单实例**程序：当 Edge 已经打开时，再运行

```cmd
netmon.exe --app "C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe"
```

新启动的 `msedge.exe` 进程会**把请求转交给已经运行的浏览器，然后立刻退出**。
它没有子进程，真正的浏览器进程（几十个）跟它没有父子关系，因此：

- 进程树里只有那个已经死掉的 PID → **一条记录都抓不到**；
- 退出后引擎会认为目标已结束 → 看起来像"监控一会儿自己停了"。

工具现在会明确把这件事说出来：

```
[warn] target exited immediately but 20 other 'msedge.exe' process(es) are running
       that were not started by us (...). This application hands off to an existing
       instance. Stop this run and use:  netmon --attach msedge.exe --keep-alive
```

**正确做法：附加到已经运行的浏览器**

```cmd
netmon.exe --attach msedge.exe --keep-alive
```

按映像名附加会**收编该映像名的全部进程**及其后代——浏览器是"一组对等进程"，
不是一个父进程带一群子进程，只取第一个只能看到一小部分流量。实测附加到
23 个 `msedge.exe` 进程后，页面访问的域名与 SNI 都能正常捕获。

图形界面里对应的是「按名称监视」输入框：填 `msedge.exe` 后点「添加名称」，
它会进入目标列表，和可执行文件一起开始监视。

**另一个选择**：先把浏览器完全关掉（所有窗口），再用 `--app` 启动。
这时新进程就是真正的浏览器根进程，也能正常工作。

### 6.4 只看某个进程的记录（进程筛选）

有些程序会把下载之类的工作交给**另外的子进程**去做。此时不需要做任何特殊配置：
用 `--app` 启动主程序，它派生出来的所有子进程（含名字完全不同的下载子进程）
都会被自动纳入监控。

实测（主程序 `BaiduNetdisk.exe` 派生 `BaiduNetdiskHost.exe`）：

```
ETW  BaiduNetdisk.exe      pid=74072   main-a.invalid
ETW  BaiduNetdiskHost.exe  pid=74616   main-a.invalid     ← 不同名的子进程也在
```

要看哪个进程，在界面里筛掉其它进程即可：

| 界面 | 操作 |
|---|---|
| 图形界面 | 「只看这些进程：」一行 → 点「选择进程…」→ 在列表里 Ctrl/Shift 多选 → 确定。右边「全部」按钮一键恢复 |

要点：

- 进程列表列出的是**已经出现过的**进程，不要求你提前知道名字——
  下载子进程在跑起来之前根本不存在，名字也无从输入；
- **父子进程请求同一个域名时，只有第一个会真正发包**。Windows 的 DNS 客户端
  有缓存，父进程刚查过的名字，子进程再查会直接命中缓存，不产生任何查询，
  因此也就没有记录可抓。这不是漏报——系统确实没有发包。
  实测同一个 helper 在两次运行中分别产生 1 条和 3 条记录，差别就来自这里。
  想验证某个进程到底有没有在解析，给它一个**独占的、没被查过的**域名；
  这也意味着**你不能用"记录少"来判断某个进程被漏掉了**；
- 匹配按**映像名**而不是 PID，所以子进程重启、或者每下载一个文件就起一个实例，
  都会继续被选中；
- 勾选会同时作用于**导出**：导出的是当前筛选后的记录；
- 不勾选任何进程 = 显示全部，不会意外把列表清空。

如果连主程序都不想启动（比如只想在它下次运行时才开始记录），用持续按名称监视：

```cmd
netmon.exe --watch BaiduNetdisk.exe --keep-alive
```

`--watch` 会持续按映像名识别进程，命中即收编，并覆盖它的全部子进程；
已经运行的和之后新启动的都算。

### 6.5 域名表与 AAAA 查询

工具会为**每个进程**维护一张域名表：该进程请求过的所有域名，去重、按字母排序。
表里的每个域名都会被独立查询 **AAAA 记录**，结果记在表里。

```cmd
:: 界面里用「域名表 (Ctrl+W)」查看每进程的域名表与 AAAA 结果
netmon.exe --app "C:\Apppp.exe" --export-domains domains.csv
netmon.exe --app "C:\Apppp.exe" --aaaa-workers 8      :: 更多查询线程
netmon.exe --app "C:\Apppp.exe" --aaaa-workers 0      :: 关闭查询
```

表里每个域名的状态是以下四种之一：

| 状态 | 含义 |
|---|---|
| IPv6 地址（一条或多条） | 存在 AAAA 记录 |
| `无 AAAA 记录` | 域名存在，但没有 AAAA 记录 |
| `域名不存在 (NXDOMAIN)` | 域名本身不存在（拼写错误等） |
| `查询失败: …` | 查询本身失败（解析器不可达、超时）——**和"没有记录"是两回事** |

后两者刻意分开：一个域名不存在和一个域名只有 IPv4，是完全不同的情况。

#### 查询是怎么跑的（为什么不影响监控）

查询**不在捕获路径上**。捕获线程只做一次哈希插入和一次非阻塞入队；
真正会阻塞的解析调用跑在**独立的工作线程**里，没有任何人等待它们的结果。

这是刻意的设计：解析一个名字是一次会阻塞的系统调用，服务器慢或不可达时可能耗时数秒。
如果放在捕获路径上，管线会被拖住，ETW 投递线程会堵在它后面，
监控就会开始丢掉它本来要收集的事件。现在无论 DNS 服务器多慢、查询挂多久、
队列积压多长，监控都不会被拖慢。

线程数用 `--aaaa-workers` 调整（默认 4）。队列满时**丢弃查询并计数**，
而不是阻塞——丢弃一次后台的补充查询是可接受的代价。

#### 什么时候查、查几次

- **每个新域名出现时查一次**。同一个域名被多个进程请求时，两张表里都会列出，
  但**只查一次**——AAAA 记录是域名的属性，不是请求者的属性。
- 因此"域名表每次更新都执行查询"的效果是：**每新增一个域名就查一次**；
  重复出现的域名不会反复查。
- 想把失败的或全部重新查一遍：图形界面的域名表窗口里有「重查失败项」「全部重查」
  按钮。网络曾经断过时这很有用——那时记下的结果不是错，只是过时，而一次采样分不出来。

#### 缓存

默认**允许使用解析器缓存**：域名通常刚被目标程序解析过，答案已在缓存里，
再发一次查询只是徒增流量。需要强制走网络时加 `--aaaa-bypass-cache`。

#### 导出

`--export-domains` 每个 (进程, 域名) 一行；同一个域名被两个进程请求就会出现两行，
因为表是按进程分的。列：`process, domain, status, ipv6, attempts, elapsed_ms`。
图形界面的域名表窗口里有「导出…」按钮，默认文件名是 `netmon-domains-<时间戳>.csv`。

> 域名表本身只负责记录；把其中的域名写进 hosts 是下一节的独立动作。
> `域名不存在 (NXDOMAIN)` 与「无 AAAA 记录」一样，按 `--no-aaaa` 策略处理：
> 默认写成 `127.0.0.1`，选 `skip` 则不写入。

### 6.6 写入 hosts

把**某一个进程**的域名表写进 hosts 文件。**一次只写一个进程**，而且要用户明确点
「写入」才动——改 hosts 会影响整台机器的解析结果，不该自动发生。

写入和删除都是**按进程**的，而且两边都只由你发起（唯一例外是你自己打开的自动模式）：
写入只影响所选进程，删除也只影响所选进程，两个进程之间互不干扰。

#### 写入规则

| 域名情况 | 写入什么 |
|---|---|
| 有可用的 IPv6 地址 | 写入**最优**的那条 IPv6 地址 |
| 没有可用的 IPv6 | 两种策略，**默认为第二种**：<br>① 不写入（保持原解析）<br>② 指向 `127.0.0.1`（禁用该域名） |

`--no-aaaa skip` 或界面里切换策略即可。

#### 写入是「追加」，不是「重写」

一次写入对每一行的处置，只有下面几种，**没有一种会删掉东西**：

| 文件里的现状 | 本次写入做什么 |
|---|---|
| 没有这个域名 | **追加**一行 |
| 已经写过，地址一样 | **不动** |
| 已经写过，`127.0.0.1`，而现在有 IPv6 了 | **更新为 IPv6 地址**（唯一会被改写的方向） |
| 已经写过，地址不同（比如别的 IPv6 地址） | **保持不变**——能用的地址不会被换掉 |
| 别的进程写过的同一个域名 | 不重复写第二行，只把本进程**登记**到那一行上 |
| 文件里本来就有（你自己的行） | **跳过**。你的行在前面，写第二行也轮不到它生效 |

预览表里「hosts 里的现状」和「本次写入」两列就是这张表的逐行展开。**没东西可写时
文件一个字节都不动**，也不会产生备份。

已经写入的行在不受影响时**逐字节保留**——包括你自己调过的空格。只有真要改的行
（追加、更新地址、加登记）才会重写。

#### 分进程：两个进程互不影响

每条记录末尾都带着**是哪些进程把它写进去的**。于是：

- 写入 A 不会动 B 的行，B 的行甚至一个字节都不会变；
- 移除 A 只删 A 的行。如果某一行是 A 和 B 都要的域名，那一行**保留**，只是把 A 的
  名字从标记里去掉，等 B 也移除时它才会消失。

没有这层记录的话，先写 A 再写 B 会把 A 的条目顶掉，或者移除 A 时把 B 还在用的
域名一起删掉——两种都是"另一个进程被殃及"，正是要避免的。

图形界面「查看 / 编辑」标签页的信息栏和「当前条目」标签页，
都会列出每个进程名下有多少条。一行被两个进程共用时**双方各计一次**，
所以这些数字相加可能大于条目总数——那表示其中有些行是两个进程共用的。

#### 「最优 IPv6」是怎么选的

hosts 文件没法表达作用域 ID，也没法写回退，所以只能挑一条。按作用域排序：

1. **全局单播**（`2000::/3`）—— 能路由到，这才是写入的目的
2. **唯一本地地址**（`fc00::/7`）—— 不能全球路由，但内网可用，比没有强
3. 其它（含回环）

**链路本地地址（`fe80::/10`）、未指定地址、IPv4 映射地址一律排除**：
链路本地地址没有作用域 ID 在 hosts 里根本用不了，写进去只会把这个域名弄坏，
而不是帮上忙。如果某个域名的 AAAA 只有链路本地地址，它就会被当作"无可用 IPv6"，
按上面的策略处理。

同类地址之间**取解析器返回顺序里的第一条**——服务器的排序本身带偏好信息，
CDN 场景下通常反映就近程度。**没有做延迟探测**，这是已知限制（见 §11.5）。

#### 条目标记

写入的条目被两层标记包住，便于识别和删除：

```text
# === NetMonitor managed entries begin === (do not edit inside the markers) ===
127.0.0.1                               github.com                               # nm msedge.exe
2606:4700:10::ac42:93f3                 www.example.com                          # nm msedge.exe,baidunetdisk.exe
# === NetMonitor managed entries end ===
```

- 区块标记：整段可以被一次性替换或移除，不会越界；
- 每行末尾的 `# nm`：即使区块标记被误删，单条记录仍能被识别出来；
- `# nm` 后面的进程名：这一行是谁写的。一行被多个进程要，名字就并列
  （进程名用逗号分隔——Windows 文件名里不允许逗号，所以不会歧义）。
  旧版本写的行尾只有 `# nm`，没有任何名字；下次为它写入时会补上。

#### 写入与清除是两件事

**写入永远不会删掉任何条目**，所以"没有可写的东西"和"要清空"再也不会混为一谈：
没有可写的内容时，文件原样不动，提示会直说"没有需要写入的改动"。

要清除，用两个明确的动作之一：

| 操作 | 影响范围 |
|---|---|
| **移除该进程的条目** | 只删当前所选进程写的那几行；与其它进程共用的行保留 |
| **移除全部条目** | 删掉本程序写入的所有行（有确认） |

> 这两条来自一次真实误报：重启程序后打开 hosts 窗口、域名表还没填上就按了「写入」，
> 结果文件被清空，看起来就像"hosts 文件自己还原了"。当时的写入是"用新计划整个
> 替换区块"，而空计划替换出来就是一个空区块。改成追加式合并之后，
> 这条路径从结构上就不存在了——合并函数里没有"删除"这个动作。

#### 备份不会被自动删除

程序**只添加备份，从不自动删除**。清理旧备份是一个需要你明确执行的操作：
图形界面的 hosts 窗口里有「清理旧备份…」按钮（默认保留最新 50 个）。

这样设计是因为：最可能有用的一份备份恰恰是最旧的那份，而按数量自动清理的规则
会第一个把它删掉。

#### 安全性

这一条是整个程序里唯一会改动系统文件的地方，所以规则很硬，且每条都有测试：

- **区块之外一个字节都不动**。文件按原始字节处理，只有标记之间的区域会变；
  行尾风格、编码、注释、别处的空白全部原样保留。
  实测：写入再移除之后，文件与原始内容的 SHA256 **完全一致**。
- **每次修改前自动备份**，恢复备份之前也会先备份当前文件——
  恢复错了不该成为最后结论。
- **原子写入**：先写到同目录的临时文件，再用 `ReplaceFileW` 一次替换。
  用 `ReplaceFileW` 而不是直接覆盖，是因为它保留目标文件的**安全描述符与属性**；
  hosts 文件有权限限制，新文件不会自动继承，悄悄放宽权限是安全问题而不是外观问题。
- **写入需要管理员权限**，失败时会明确说明。

#### 自动模式

打开后，所选进程（可以多个）的**域名表一有变化就自动写入 hosts**，不需要每次手动点。
多进程时，同一条域名只写一行，`# nm` 后并列记录所有解析过它的进程。

- 图形界面：「自动模式」复选框

它不会一有变化就写，而是等两个条件都满足：

1. **所有已选进程的域名全部查询完毕**。域名一出现在表里、它的 AAAA 答案还要几毫秒
   才回来；如果在这中间写，有 IPv6 的域名会先被写成 `127.0.0.1`，然后立刻被改回来——
   中间那一下是错的，而且每个域名都要多赔一对备份。
2. **计划稳定 1.5 秒**。一个页面加载会在几百毫秒里加上几十个域名，
   否则每一个都会触发一次重写。

另外两条边界，都是刻意的：

- **自动模式只写入、不删除**。域名表变空时它什么都不做——清空区块仍然是需要你
  明确操作的事，免得域名表意外清空就把 hosts 内容抹掉。它也不会清理备份文件：
  自动模式可能跑很久，但删文件是你的决定，不是它的。它写入时走的是和手动写入
  完全相同的合并逻辑；多进程合并成一次文件改动、一次备份。
判断"要不要写"是拿**这次合并会不会改动文件**来定的（把计划并进文件里，看看结果
和现在是否一样），而不是和记住的状态比，也不是拿整份区块和单个进程的计划比——
后者会因为区块里还有别的进程的条目而永远判定"有变化"，每 1.5 秒重写一次。

#### 界面操作

| 入口 | 操作 |
|---|---|
| 工具栏「写入 hosts (Ctrl+H)」 | 「写入」标签页：**右键多选进程（绿色）**、选策略、**自动模式开关（支持多进程）**、预览表格（含“进程”列）、写入（多进程合并为一次）、**写入所选域名（右键，可跨进程）**、**移除所选进程的条目**、移除全部条目…、备份、恢复备份…<br>「当前条目」标签页：hosts 文件里**现在**由本程序写入的条目，按进程分组；**右键可复制该行或删除该行**<br>「查看 / 编辑」标签页：直接编辑并保存 |

**没有「预览」按钮**：切换进程（可多选）、切换无 IPv6 策略、域名表变化（新域名、
AAAA 结果落定、自动写入完成）都会让预览自己更新，约 1.2 秒内跟上。这个间隔是
刻意加的——一个页面加载会产生几十次变化，每次都去问一遍引擎是浪费。
刷新期间已选中的行会保留。

**多选进程**：在进程列表上**右键**选择/取消选择、全选或全不选；已选择的进程
显示为绿色，列表下方会写明选了几个。预览表把它们计划合并显示，每行都标出属于
哪个进程。点「写入 hosts」把所有已选进程合并成一次写入（一次备份）；两个进程
写同一条域名时只写一行、并列记录归属。「移除所选进程的条目」同理，仍按进程逐个
处理。

**只写选中的域名**：在预览表里 `Ctrl`/`Shift` 多选，右键选「写入所选域名」。
选中的行可以来自不同进程，引擎合并成一次写入；写入范围缩小到这些域名，规则不变：
有 IPv6 的写最优 IPv6，没有的仍按当前策略处理，已经被写过的保持原样。
自动模式不受预览选择影响，仍然写已选进程的整个域名表。

**「当前条目」的右键菜单**：

| 菜单项 | 作用 |
|---|---|
| 复制该行 | 把 hosts 文件里的这一行原样放进剪贴板（含 `# nm` 归属标记） |
| 删除该行… | 只删这一行；若该行同时属于多个进程，确认框会明确提示“所有进程都不再拥有它”。删除前自动备份，改动写入历史记录 |

#### 查看与编辑

程序内可以查看和编辑 hosts 文件：图形界面「查看 / 编辑」标签页里就是普通的文本框，
改完点「保存」。

保存是**整体替换**文件内容（这正是"编辑"的含义），安全性由保存前自动备份保证。
保存会先让你确认。
如果你在编辑器里把标记删掉了，那段内容就变成普通行，按进程移除不会再认它——
这是你的选择，程序不会去猜。反过来说，**手动往区块里加的行**没有进程名，
第一次为某个进程写入时会被登记到那个进程名下。

#### 关于 NXDOMAIN

`域名不存在 (NXDOMAIN)` 的域名，在默认策略下会被指向 `127.0.0.1`。
如果你打算用它来"禁用"某些域名，这正是想要的效果；如果只是想记录，
用 `--no-aaaa skip` 跳过它们。

#### 重启之后：本地缓存

hosts 条目比产生它的那次会话活得久。程序退出再打开后，如果域名表是空的，
你既看不到"这些条目是谁写的、当时解析到什么"，也没有办法在界面里选中那个进程
去移除它——只剩"移除全部"一条路。所以这两样东西会**存在本地**：

| 文件 | 内容 | 位置 |
|---|---|---|
| `domain-tables.json` | 上次会话每个进程的域名表（含 AAAA/A 结果与查询时间） | `--data-dir`，默认可执行文件旁的 `netmon-data` |
| `hosts-history.ndjson` | 每一次 hosts 改动的记录：时间、动作、进程、增删条数、备份路径 | 同上 |

启动时自动载入。于是：

- **域名表里会出现上次会话的进程和域名**，状态列标注 `·上次会话`，用另一种颜色；
- **hosts 窗口的进程列表**同时包含"当前会话的进程"和"文件里写了条目的进程"，
  所以哪怕那个程序根本没在跑，也能选中它，预览出它的域名，按进程移除；
- **hosts 更改记录**跨重启保留，能看到谁在哪天写了什么、删了什么。

几条边界：

- **自动模式只写本次会话真实解析到的域名**。缓存里的地址是上次的观测结果，
  没有重新解析就写回去，等于把一个可能已经过期的地址当成现状——所以自动模式
  直接忽略这些行（手动写入不受限，因为那是你明确要求的）。
- 域名行保留 **90 天**；但**只要它在 hosts 文件里还有条目，就一直保留**，
  与年龄无关——这些正是缓存存在的理由。
- 缓存是普通文件，**可以直接删**（`netmon-data` 整个目录），下次启动从空开始；
  也可以用 `--no-cache` 临时关掉。
- 重新打包发布目录时，脚本会把这个目录**保留下来**，但**不会放进 zip**：
  里面是你访问过的域名。

### 6.7 推荐流程

1. `run-netmon-gui.cmd`（或 `netmon.exe --app "<目标路径>"` 走无界面输出）——
   监控与目标同时就绪；
   浏览器等已在运行的单实例程序改用 `netmon.exe --attach <映像名> --keep-alive`（见 §6.3）；
2. 目标运行时界面实时刷新；
3. 结束后在界面里导出，或用 `--export` 让无界面模式在退出时写文件。

### 分工

窗口是 Python 写的，**抓包仍然是 Rust 引擎**。GUI 以 `--stream-json` 模式启动
`netmon.exe`，逐行读取它输出的 NDJSON（每行一个 JSON 对象）并渲染。
这样做的理由：域名捕获对延迟和丢包极其敏感，必须在内核事件回调里用原生代码完成；
而界面是交互问题，Python 能以最少的代码做出原生文件对话框、可排序表格和实时过滤。
两者通过一条有明确格式的管道解耦，任何一方卡住都不会影响另一方。

引擎输出的是逐行 JSON；完整的对象与命令清单见 §8.5。这里的界面只消费其中几类：
`hello`、`log`、`record`、`status`、`domain`、`aaaa`、`summary`、`fatal`，
以及 hosts 窗口用的 `hosts_*`。

## 9. 工作原理

### 9.1 数据源

**主源：ETW `Microsoft-Windows-DNS-Client`**

订阅事件 3006（发起查询）与 3008（查询完成）。这两个事件由**调用方线程**写入，
所以事件头里的 `ProcessId` 就是发起查询的应用程序。

这一点是实测确认的，不是推测：用一个已知 PID 的 `ping.exe` 查询随机域名，
观察到的 3006/3008 事件 PID 与 `ping.exe` 完全一致；同理观察到 `msedge.exe`、
`perfmon.exe`、`lsass.exe` 各自的查询。该提供程序另有 1001/1015/1017/3009–3020
等事件，那些由 DNS Client 服务（`svchost.exe`）写入，携带的是服务进程 PID，
不包含应用信息，本工具在回调里用一次整数比较就把它们滤掉了。

**补充源：Npcap 抓包（UDP/53）**

覆盖自带 DNS 解析器的应用。查询包的源端口通过内核 UDP 端点表
（`GetExtendedUdpTable`）反查属主进程。属主是 `svchost.exe` 的行会被**抑制**——
那些是 Windows 解析器自己发的包，ETW 已经用更好的归属覆盖了，再报一次只会造成重复。

**DoH/DoT 补充：TLS SNI**

从 443 / 853 的 TLS ClientHello 的 `server_name` 扩展中恢复域名，
SNI 的归属通过**TCP** 端点表（`GetExtendedTcpTable`）反查。

### 9.2 进程归属

```
                 ┌──────────────────────────────┐
ETW 回调 ────────▶ 事件 3006/3008？ ──否──▶ 丢弃（一次比较）
                 └──────────┬───────────────────┘
                            │ 是
                            ▼
              PID 在"已确认非目标树"集合里？ ──是──▶ 丢弃
                            │ 否（未知 PID 一律放行）
                            ▼
                     解析域名+类型 → 入队
                            │
                            ▼
   ┌──────────────────  管线线程  ──────────────────┐
   │ 不在目标树？ → 立即快照一次并向上追溯父链       │
   │   ├ 是目标后代 → 收录，并记住该 PID             │
   │   └ 否         → 丢弃并计数                     │
   │ 去重 → 关联 → 建记录 → 入环形缓冲               │
   └────────────────────────────────────────────────┘
```

- **进程树监视线程**每 150 ms 做一次 `CreateToolhelp32Snapshot` 快照，
  重算目标 PID 的**后代闭包**。一次完整快照几十微秒，且完全不碰捕获线程。
- **成员资格有宽限期**：PID 从快照消失后仍保留 20 秒。
  `git`、`curl`、一次性更新器这类短命子进程可能在两次快照之间完成解析并退出，
  它们的事件仍必须被正确归属。
- **未知 PID 立即追溯**：事件来自从未见过的 PID 时，当场做一次快照并沿父链上溯，
  判断目标是否为祖先，是则立即收编。这堵住了"子进程刚创建就发查询"的窗口。
- **快速否定过滤**：已被完整祖先判定证明**不属于**目标树的 PID 会进入一个集合，
  ETW 回调用一个哈希查找就能挡掉它们。未知 PID **一律不挡**，
  所以不可能因此漏掉新生的子进程。

### 9.3 线程模型

| 线程 | 职责 | 阻塞方式 |
|---|---|---|
| ETW 投递线程 | 解析域名与类型，入队 | `ProcessTrace` 阻塞在内核 |
| Npcap 线程（每接口一个） | 解包、解析 DNS/SNI、反查端口属主、入队 | `pcap_next_ex` 阻塞在驱动 |
| 进程树监视线程 | 每 150 ms 刷新后代闭包 | 定时休眠（不涉及捕获路径） |
| 管线线程 | 进程归属、去重、IP 缓存、建记录 | 阻塞在 channel 上 |
| 主线程（输出循环） | 取新记录写入 stdout / NDJSON，采集状态 | 60 ms 短休眠（不涉及捕获路径） |

捕获线程之间通过 **crossbeam 有界队列**（容量 262144）通信，快速路径无锁。
队列满时 `try_send` 立即失败并计数，绝不阻塞 ETW 投递线程——
丢一个事件可以接受，卡住 `ProcessTrace` 不行。

**关于刷新率**：捕获路径 100% 事件驱动，没有定时器。
主循环每 60 ms 取一次新记录（延迟上限就是这个数），
`status` 对象按 `--status-interval-ms`（默认 500 ms）发出；
这两者都只是读取已经到达的数据，不会回溯影响采集。

### 9.4 缓冲区

| 层 | 配置 | 理由 |
|---|---|---|
| ETW 会话 | 128 KB × 64–512 个缓冲区 | 缓冲是分页的，只有在负载下才驻留内存；这是抵御突发最便宜的手段 |
| Npcap | 每句柄 8 MiB + 立即模式 | Npcap 默认 1 MiB，一次 TLS 握手突发就能撑爆 |
| 应用队列 | 262144 条 | 见上 |

## 10. 常见问题与排查

### 10.1 先跑自检

```cmd
netmon.exe --doctor
```

会检查：是否管理员、ETW 会话能否建立、DNS 提供程序能否启用、
Npcap 设备列表、BPF 过滤器能否安装。绝大多数问题在这一步就能定位。

### 10.2 提示 "could not start ETW session"

- **权限不足**：ETW 实时会话通常需要管理员，用 `run-netmon.cmd`（会自动提权）。
  注意这只在真正失败时才是原因——实测出现过**令牌未提升但 ETW 与 Npcap 都正常**
  的情况，所以工具不把"是否管理员"当作判据，而是看数据源实际有没有起来
  （`--doctor` 的 `etw session` 一行、图形界面状态栏的 `ETW`/`PCAP` 计数）。
- **策略限制**：域策略可能禁止跟踪会话，或当前账户不在
  "Performance Log Users" 本地组里。
- **残留会话**：上一次异常退出可能留下同名会话。工具会自动尝试停止并重试一次；
  仍失败时手工执行 `logman query -ets` 查看，`logman stop <名字> -ets` 停止。

### 10.3 "Npcap source unavailable"

- 驱动没装或没运行：`sc query npcap` 应显示 `RUNNING`。
- 没装驱动 → 运行 `install-npcap.cmd` 或 `npcap-1.79.exe /S /winpcap_mode=yes`。
- 装了但没运行 → 看 `%SystemRoot%\System32\Npcap\NPFInstall.log`；
  常见原因是安装后没有重启，或安全软件拦截了驱动加载。
- **注意**：Npcap 缺失时 ETW 主源仍可用，只是少了自带解析器应用的覆盖与 SNI。

### 10.4 界面没有任何记录

按顺序检查：

1. **目标设了吗？** 标题栏 `Target` 若是 `(none …)`，点「浏览…」选择。
2. **在捕获吗？** 状态徽标应为 `* LIVE`。
3. **目标真的发查询了吗？** 域名可能已在 DNS 缓存里——`ipconfig /flushdns` 后再试。
   注意：应用请求一个**已缓存**的域名不会产生 3006 事件，这是系统的行为，不是漏报。
4. **过滤条件太严？** 点「清除过滤」恢复全部记录与数据源。
5. **看「日志 (Ctrl+G)」**，里面有各数据源的启动结果与逐项计数。

### 10.5 ETW 报"系统资源不足"（os error 1450）—— **这是最常见的问题**

症状：界面/输出里出现

```
ETW source unavailable: could not open ETW session '...': 系统资源不足，无法完成请求的服务。 (os error 1450)
```

然后**列表一直是空的**，或者只有零星几条。原因与解决办法：

**原因**：普通（非私有）ETW 实时会话的寿命长于创建它的进程。如果 NetMonitor 被
强制结束——任务管理器结束任务、直接关掉窗口、崩溃——**会话会留在系统里**，
继续占用内核 ETW 资源。积累到一定数量后，再创建会话或启用提供程序就会返回 1450。

此时 ETW 主数据源已经失效，只剩抓包源；而抓包源看到的 DNS 包属主是 `svchost.exe`
（被抑制，见 §9.1），所以目标应用的查询一条都看不到——**看起来就是"完全没有输出"**。

**工具已经内置了三层自愈**：

1. 启动时自动清理"属主进程已不存在"的残留会话，并在日志里说明清理了哪些：
   ```
   [warn] cleared 1 trace session(s) left behind by a terminated run: NetMonitor-1234
   ```
   只清理属主进程确实已消失的会话，所以**不会误伤你故意并行运行的第二个实例**。
2. 如果创建会话时仍然撞上 1450，会再清理一次并重试。
3. 手动兜底：

```cmd
netmon.exe --clean-sessions          :: 停掉所有 NetMonitor 残留会话
netmon.exe --doctor --clean-sessions :: 清理后再做环境自检
```

> 开发过程中实测：连续 5 次 `taskkill /F` 强杀，修复前第 2 次起 ETW 就永久失效；
> 修复后每次启动自动清掉上一条残留，ETW 始终可用。详见
> X

**预防**：尽量用正常方式退出（图形界面点「停止」后关窗；无界面模式让它自然到期，
或按一次 `Ctrl+C` 让清理逻辑执行），这样会话会被正常停止。

### 10.6 顶部出现 `drops: kernel N`

内核或驱动层丢了事件。说明消费者跟不上：

- 减小抓包范围：用 `--pcap-filter` 收窄 BPF，或 `--no-npcap` 只留 ETW。
- 关闭不需要的数据源显示（界面里的数据源勾选框）。
- 机器本身在跑满带宽的下载时，抓包线程被抢占是正常的；
  此时建议 `--no-npcap`，因为 ETW 主源不受影响。

### 10.7 某些域名没抓到

见 §12 的限制章节。最常见的原因是 **DoH**（浏览器默认开启）——
查询内容加密传输，无明文域名可读；只能靠 SNI 补回主机名，且带
`owner inferred from a recent DNS lookup` 标记或用 SNI 源显示。

### 10.8 排查"事件到底被哪一道过滤器丢掉了"

设置环境变量 `NETMON_FILTER_LOG=<文件路径>`，程序会把**每一个事件**的取舍决定
逐行写进该文件。当出现"什么都没有抓到"时，这能直接回答是哪个环节丢的：

```
1791988088.527  etw-forward    pid=31552 kind=Query name=b-22347.invalid
1791988088.528  etw-foreign    pid=17016 id=3006
1791988088.529  pipeline-accept pid=32196 name=b-22347.invalid
1791988088.530  pipeline-reject pid=29260 name=x.com roots=[31552] members=1
```

| 标记 | 含义 |
|---|---|
| `etw-foreign` | 被 ETW 回调里的否定过滤器挡掉（该 PID 已被证明在目标树外） |
| `etw-malformed` | 事件负载不是预期的域名格式 |
| `etw-forward` | 已解析并送进管线 |
| `pipeline-accept` | 已归属并记录 |
| `pipeline-reject` | 管线判定不属于目标树（后面附当前的根列表与成员数） |

未设置该变量时完全不产生开销。注意开启后会有额外的文件写入，
**时序敏感的复现可能会因此改变**——这本身也是一个有用的信号。

## 11. 性能说明与限制

### 11.1 实测性能

测试机：Windows 11 26100，16 逻辑核，Npcap 1.79。数据见
[`TEST-REPORT.md`](TEST-REPORT.md)。

| 场景 | 查询数 | 丢包 | CPU（单核占比） | 工作集 |
|---|---|---|---|---|
| 常速（1 个目标 + 1 个子进程） | 240 / 19 s | 0 | 7.2% | 36 MB |
| 突发（1 个目标 + 16 个子进程并发解析 40 个域名） | 1360 / 20 s | 0 | 9.8% | 37 MB |

突发场景下仍为 0 丢包。

### 11.2 "无法归属"的行默认不显示

某行若既没有 ETW 事件、也没能从端点表反查出属主（例如套接字已经关闭），
它的 PID 记为 0。**这类行不能作为"目标产生了这次查询"的证据**，
所以默认丢弃并计数。想查看它们：界面勾选「无法归属」，或命令行加 `--show-unattributed`。

这是刻意的取舍：宁可少报，不可误报。

### 11.3 SNI 归属可能是推断值

快速关闭的连接（探测、失败握手、短请求）在抓包线程去查 TCP 表时端口可能已经释放。
此时工具会回退到"**该域名最近被哪个目标树进程解析过**"的关联判断，
并在 `detail` 中明确标注 `owner inferred from a recent DNS lookup`。
这是关联而非测量，请据此评估可信度。关联窗口 60 秒，且只有已经通过进程树
校验的 PID 才会进入这张表，所以它不会把范围扩大到目标树之外。

### 11.4 覆盖不到的查询

| 情形 | 是否能捕获 | 说明 |
|---|---|---|
| 走 Windows 解析器的普通查询 | ✅ ETW，PID 精确 | 绝大多数桌面应用 |
| 应用自带 DNS 解析器（明文 53） | ✅ Npcap + UDP 端点表 | |
| DNS over TCP（53） | ✅ Npcap | 较少见 |
| **DoH（HTTPS 加密 DNS）** | ⚠️ 只能靠 SNI 补主机名 | 查询内容不可见；Chrome/Edge 默认开启，可在设置里关掉"安全 DNS"以恢复完整可见性 |
| **DoT（853 加密 DNS）** | ⚠️ 只能靠 SNI 补主机名 | 同理 |
| **DoQ（QUIC 加密 DNS）** | ❌ 无法获取域名 | QUIC 的 SNI 在加密的 Initial 包里 |
| **ECH（加密客户端问候）** | ❌ SNI 也被加密 | 目前部署有限 |
| 命中 DNS 缓存、未产生查询 | — | 系统就没有发查询，无从捕获 |
| 运行时间短于 150 ms 的子进程 | ⚠️ 有宽限期兜底 | 事件若在进程消失后才到，靠 20 秒宽限窗口仍能归属 |
| 目标进程以另一用户身份运行 | ❌ | 无法读取其进程信息 |

### 11.5 已知边界

- **不解析 IPv6 扩展头**。实践中 DNS 与 TLS 不会藏在扩展头之后，未做处理。
- **不重组 IP 分片**。超大 ClientHello 若被分片，SNI 可能取不到。
- **环形缓冲上限 200000 条**。超出后淘汰最早的记录并计数（统计里的 `evicted`）。
  长时间会话建议定期导出后清空。
- **进程名取自快照**。进程退出后仍能在宽限期内显示名字。
- **同一查询的 ETW 与 PCAP 双份记录**：若某应用既走系统解析器又被抓到明文包，
  且两次归属到不同 PID，会出现两行。属主是 `svchost.exe` 的 PCAP 行已被抑制，
  所以这种情况很少见。

## 12. 磁盘布局

所有安装目录、缓存、构建产物都放在项目盘（本例为 `D:`）。

| 路径 | 内容 | 实测大小 |
|---|---|---|
| `<项目>\.toolchain\rustup\` | Rust 工具链 | 591 MB |
| `<项目>\.toolchain\cargo\` | cargo 主目录、crate 源码缓存 | 487 MB |
| `<项目>\.cache\target\release\` | release 构建产物 | 684 MB |
| `<项目>\.cache\target\debug\` | debug 构建产物 | 1.2 GB |
| `<项目>\.cache\dl\` | 下载的安装包与压缩包 | 14 MB |
| `<项目>\.cache\deps\` | 解压后的 Npcap SDK | 1.7 MB |
| `<项目>\dist\` | 打包产物（含 zip） | 6.3 MB |
| `<发布目录>\netmon-data\` | **运行期**缓存：域名表快照、hosts 更改记录（默认位置，可用 `--data-dir` 改） | 随使用增长，通常几十 KB～几 MB |
| `<发布目录>\hosts-backups\` | 每次改 hosts 前的备份 | 每个约 1–2 KB |
| **C 盘：`C:\Program Files\Npcap\`** | 安装器副本、卸载器、诊断脚本 | 1.6 MB |
| **C 盘：`System32\drivers\npcap.sys` + `System32\wpcap.dll` + `Packet.dll`** | 驱动与运行库 | 763 KB |
| **C 盘合计** | | **约 2.4 MB**（不可迁移，见 §4.2） |

可以只保留 release 产物来省空间：删除 `.cache\target\debug\` 即可回收 1.2 GB。

环境变量（`install.ps1` / `build.ps1` 自动设置）：

```
RUSTUP_HOME      = <项目>\.toolchain\rustup
CARGO_HOME       = <项目>\.toolchain\cargo
CARGO_TARGET_DIR = <项目>\.cache\target
NETMON_NPCAP_SDK = <项目>\.cache\deps\npcap-sdk
```

`rustup-init` 使用 `--no-modify-path`，不会改动用户 PATH，
也不会往 `%USERPROFILE%\.cargo` 写任何东西。
