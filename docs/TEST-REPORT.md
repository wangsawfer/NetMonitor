打包后从 `run-netmon-gui.cmd` 启动时又暴露了两个真实缺陷，都已修复：

- **批处理启动器把参数传坏了。** 第一版在 `rem` 注释里写了双引号（批处理对
  rem 行里的引号处理不一致），又用了 `start`（它会重新解析命令行）。
  实测结果是 `--args` 后面的目标域名全丢，引擎拿到一堆垃圾参数、跑完就退出，
  界面显示"已开始监控"却一条记录都没有——和用户报的现象一模一样。
  现在注释里不含引号，也去掉了 `start`。
- **`--args` 只吃一个 token。** 用户自然会写
  `--args --fork 3 example.com github.com`，而旧实现只取 `--fork`。
  改为吞掉其后全部内容，并在手册里注明"必须放在最后"。

这两个缺陷的价值在于：它们只在**真实启动路径**（双击 .cmd）上出现，
直接 `python gui/netmon_gui.py` 完全测不出来。

过程中修复了一个真实缺陷：排序后表格出现
`_tkinter.TclError: Item N already exists`。
`_rebuild_table()` 重建了整个表格，却没有同步"已渲染到第几条"的游标，
紧随其后的增量渲染于是把同一批记录又插了一遍，而 Treeview 的 iid 就是序号。
修好之后排序、过滤、清空三条路径都会正确推进游标。

## 6. 开发过程中发现并修复的真实缺陷

以下每一项都是实测发现、已修复、并有对应回归测试的。记录在此，因为它们说明了
测试覆盖到了哪些"想当然会导致错误"的地方。

### 6.1 BPF 优化过滤器静默漏掉 IPv6（严重）

最初使用的过滤器是教科书式的"首个负载字节为 TLS 握手"写法：

```text
(tcp dst port 443) and (tcp[((tcp[12] & 0xf0) >> 2)] = 0x16)
```

它能编译、能装载、**但对 IPv6 ClientHello 一条都不匹配**。在双栈机器上
`getaddrinfo` 按 RFC 6724 优先返回 AAAA，于是绝大多数 HTTPS 连接的 SNI 都取不到。

定位方式：先用宽过滤器 `tcp port 443` 验证拿到 SNI，收缩到该表达式后消失。

修复：改用端口级过滤器，把 0x16 判断放到用户态（本来就有，成本是一次字节比较）。
端口过滤器多放行的包量很小——实测 20 秒内 5357 个包，且已关闭混杂模式，
只会看到本机流量。**正确性优先于这个微优化**。

> 附带教训：一个"悄悄丢掉它本该选中的流量"的抓包过滤器，比没有过滤器更糟。

### 6.2 被监控目标会写花界面

目标进程由控制台父进程启动时会继承同一个控制台。只要它输出一行文本，
就会落在 ratatui 差分渲染的屏幕中间；渲染器认为那些格子还是它写的内容，
于是损伤会一直累积。实测表现为字符丢失、旧帧残留。

修复：界面模式下把目标的 stdin/stdout/stderr 指向空设备（`--child-console` 可关闭）；
无界面模式则保持继承，因为那里目标的输出是有用的。

### 6.3 鼠标"任意移动都上报"导致事件风暴

crossterm 的 `EnableMouseCapture` 会同时打开 DECSET 1000、1002 **和 1003**。
1003 是"任何移动都上报"，Windows 控制台严格执行：只要指针在窗口上，
就不停地产生 `MOUSE_MOVED` 记录。

用 `NETMON_INPUT_LOG` 实测：12 秒内收到约 1800 个鼠标移动事件，
每个都唤醒一次事件循环去做一次毫无变化的渲染。

修复：只写 `?1000h` 与 `?1006h`（按键 + SGR 坐标），不启用 1003；
同时让事件循环对 Moved/Drag 完全不重绘。修复后同样 12 秒内只有 3 个事件。

### 6.4 QuickEdit 吞掉鼠标点击

控制台默认开启 QuickEdit。开启时鼠标按下被用于文本选择，**不会**上报给程序，
工具栏按钮永远收不到点击。

修复：运行期关闭 `ENABLE_QUICK_EDIT_MODE`（并置 `ENABLE_EXTENDED_FLAGS`），
退出时恢复原值。验证见 §5.3 与 §5.4。

### 6.5 表头第二行被裁掉

表头块高度是 3 行，而"边框 + 两行内容 + 边框"需要 4 行，
`Uptime / Tree / Sources` 那一行被静默裁掉。

修复：表头高度改为 4；并补上断言这两行可见的回归测试。

### 6.6 过长的快捷键提示导致整屏滚动

提示行约 200 字符，超出 120 列后被裁切。裁切后的尾部让 Windows 控制台在最后一行
最后一格留下"待换行"状态，下一次写入就把整个缓冲区上滚一行——实测表现为
表头顶端边框消失、末行文字互相叠加。

修复：`legend_for(width)` 只拼接能放下的提示项，从源头上不再产生超宽行。
测试覆盖 24 / 40 / 60 / 80 / 100 / 120 / 140 / 200 各宽度。

### 6.7 SNI 归属存在竞态

抓包线程读到 ClientHello 后去查 TCP 端点表，但发完就关闭的连接
（探测、失败握手、短请求）此时端口已经释放，查不到属主，
于是这些行因 PID=0 被丢弃——表现为 SNI 时有时无。

修复：增加"域名 → 最近解析它的进程"关联表作为回退，窗口 60 秒，
并在 `detail` 中明确标注 `owner inferred from a recent DNS lookup`。
该表只记录**已经通过进程树校验**的 PID，因此不会把范围扩大到目标树之外。

### 6.8 单实例程序（浏览器）：什么都抓不到，并且会话自己结束（用户报告）

**症状**（用户报告）：监控 Edge 时"监控一会儿就自己停止了，而且没有任何输出"。

**诊断**：

1. 检查现场发现 Edge **已经在运行**（18 个进程，根进程 PID 54336）；
2. 对照实验：让引擎监控一个"立刻退出"的目标，测得引擎在**目标退出 3.18 秒后**
   自行结束（`POST_EXIT_GRACE`）——这就是"自己停止"；
3. 再看因果：`msedge.exe` 在已有实例时会把命令行转交给它并**立即退出**，
   真正的浏览器进程与它没有父子关系，所以进程树是空的——这就是"没有输出"。

两个缺陷叠加，构成了用户看到的现象。

**修复**：

| 缺陷 | 修复 |
|---|---|
| 目标退出即结束会话 | 新增 `--keep-alive`；图形界面始终传它。停止条件也从"目标进程没了"改为"**整棵树**都没有存活成员了" |
| 启动已运行的单实例程序等于没启动 | 检测到"目标秒退 + 存在同类映像名且不在树内"时，明确报出这件事和可用的替代命令 |
| `--attach` 只收编第一个匹配进程 | 改为收编该映像名的**全部**进程；浏览器是一组对等进程，只取第一个只能看到一小部分流量 |

**实测（用户报告的原始场景）**：


### 6.9 陈旧的"非目标进程"集合会吞掉目标的**第一批**查询（严重）

**症状**：用 `--app` 监控一个启动后很快完成工作的程序（几百毫秒内解析几个域名然后退出），
**一条记录都抓不到**，而 `filtered out (other processes)` 计数却在增长。

**定位**：ETW 回调里有一个廉价的否定过滤器——一个"已确认不属于目标树"的 PID 集合，
命中就直接丢弃，连解析都不做。该集合由进程树监视线程每 150 ms 重算一次。
问题出在写入时机：

1. 监视线程在目标**尚未启动**时取快照，此时所有进程看起来都是"非目标"；
2. 期间目标被启动并收编；
3. 监视线程把**基于旧快照**的集合写了进去，其中包含刚被收编的目标 PID；
4. 目标随后的第一批查询在廉价过滤器处被丢弃，归属逻辑根本没机会看到它们；
5. 150 ms 后下一次扫描会纠正这个集合——但那时目标往往已经做完所有查询了。

这也解释了为什么早期的测试都用 `--fork`（父进程活得更久）——它无意中掩盖了这个 bug。

**修复**：把集合的发布移进 `TreeTracker::refresh()`，在**持有进程树锁的同一段临界区**里
完成计算与发布（`publish_foreign`）。调用方原本在释放锁之后再写入，才留下了这个窗口。
同时删掉了两处手动 `clear()`——它们本身就是竞态的另一个来源。

**回归测试**：`adopted_roots_are_never_published_as_foreign` 断言被收编的根进程
永不出现在对外发布的集合里；`nothing_adopted_publishes_every_process_as_foreign`
覆盖"尚未收编、正在等待"的形态。

**验证**：修复后主程序 + 不同名子进程的短命目标正常捕获：

```
ETW  BaiduNetdisk.exe      pid=74072   main-17634-a.invalid
ETW  BaiduNetdiskHost.exe  pid=74616   main-17634-a.invalid
```

### 6.10 显式收编的根进程被扫描误删（严重，开发中自伤）

**症状**：`scriptserify.ps1` 从 12/12 掉到 9/12，三项断言全挂——目标跑得好好的，
监控却一条都没抓到，且 `filtered_out of tree` 持续增长。

**引入原因**：为支持"按名称监视"而加的根进程回收逻辑：

```rust
self.roots.retain(|r| alive.contains(r) || children.contains_key(r));
```

它的本意是回收"已经死透且没有存活子进程"的发现型根进程。但目标是在
`CreateProcess` 之后**立刻**被收编的，如果那次 `refresh()` 的快照恰好还没包含
这个刚诞生的进程，`alive` 和 `children` 里都没有它——于是**刚被收编的根进程
当场被删掉**，下一次扫描发现根列表为空，清空成员集合，此后所有事件都被拒绝。

**为什么难以发现**：它依赖"快照与 spawn 的竞态"，不是每次都发生，表现为
"有时能抓、有时完全抓不到"。

**修复**：把根拆成两类——
`explicit_roots`（用户明确指定的：启动的目标、附加的进程、启动时匹配到的）
**永不自动回收**，只有下一次 `set_roots` 会替换它；
`discovered_roots`（`--watch` 按名字发现的）才在死透且无子进程时回收。

**回归测试**：`explicit_root_survives_a_sweep_without_it`——
用一个必然不存在的 PID 当根，`refresh()` 后它必须还在。

> 一般性教训：回收逻辑必须能区分"用户要求盯着的"和"我顺手发现的"。

### 6.11 排查过程中的两个自我干扰

记在这里是因为它们都**伪装成了产品缺陷**，各浪费了一轮排查。

**(1) 诊断代码自身死锁。** 为了查"事件被哪一道过滤器丢掉"，加了
`NETMON_FILTER_LOG`。第一版在一条 `format_args!` 里写了两次 `tree.lock()`：

```rust
tree.lock().unwrap().debug_roots(),
tree.lock().unwrap().live_member_count()
```

Rust 里函数实参的临时值活到整条语句结束，于是第二个 `lock()` 与第一个**自死锁**，
管线线程在第一个被拒事件上永久卡住。日志里因此一条管线记录都没有——
这个"什么都没有"又恰好很像我在查的那个 bug。

**(2) 把 DNS 缓存当成了丢包。** 用"主进程拉起不同名 helper"做验证时，helper 有时
完全抓不到，一度以为是竞态。实际上 testapp 给 helper 传的是**和父进程相同的域名**：
父进程刚查过，子进程再查直接命中 DNS 客户端缓存，**根本不会发包**。
给 helper 一个独占域名后，归属成功率 100%。

这条不是缺陷，是系统行为，已写入手册 §6.4 的要点里。

### 6.12 域名表 / AAAA 功能中修掉的两个缺陷

**(1) 把"没有该类型的记录"当成了查询失败。**

`github.com`、`ipv4only.arpa` 明明只是没有 AAAA 记录，却显示为
`查询失败: 为 DNS 查询找不到记录 (os error 9501)`。

原因：`DnsQuery_W` 报告"该类型没有记录"时用的是**两套不同的返回码**，
取决于答案是来自缓存还是来自网络：

- `DNS_INFO_NO_RECORDS` (9501) —— 属于 `DNS_INFO_*` **信息类**，不是错误
- `DNS_ERROR_RECORD_DOES_NOT_EXIST` (9701)

第一版只把 `ERROR_SUCCESS` 和 `DNS_ERROR_RCODE_NAME_ERROR` 当作答案，
这两个码就落进了"失败"分支。

修法：两者都映射为"无 AAAA 记录"，同时保留 `9003 NXDOMAIN` 为独立状态——
域名不存在和域名只有 IPv4 是完全不同的情况，合并会误导使用者。

**独立验证**：用 PowerShell `Resolve-DnsName -Type AAAA` 与 `nslookup -type=AAAA`
交叉核对，四个域名的结论完全一致（`www.example.com` 的两条地址也逐字节相符）。

**(2) 统计面板把"无 AAAA"算成了"有 AAAA"。**

截图里显示 `AAAA 4`，但六个域名里只有两个真有 AAAA 记录。
原因是 `AaaaAnswer` 有两种方式表达"没有地址"——空地址列表，和 `NoRecord`——
而计数分支只处理了前者。

这是**看着截图发现的**：列表里的每一条文字都对，只有汇总数字在撒谎。

修法不是在计数处补一个分支，而是**消除重复表达**：
`query_aaaa` 现在把空地址列表统一归一化为 `NoRecord`，
于是"没有 AAAA"只有一种写法。计数处再加一条 `debug_assert` 把这个不变量钉住。

> 教训：当一个概念有两种表示法时，早晚会有一处代码只处理其中一种。

### 6.13 改变目标后界面冻结（用户报告）

**症状**：图形界面里改动「或附加到」再点开始监控之后，主界面不再更新、
看起来像监控停了、域名表也学不到新进程。

**复现**：驱动脚本按"监控主程序 → 改成附加模式 → 再切回启动"三步走，
第二步就抛出：

```
_tkinter.TclError: Item 1 already exists
```

**根因（三个独立缺陷叠加）**：

1. **界面刷新循环不是异常安全的。** `_pump` 在**最后一行**把自己重新排期，
   所以它内部任何一处未捕获的异常都会让定时器彻底停摆。引擎还在跑，
   只有界面死了——而且是静默地死。
2. **跨会话的行 ID 冲突。** Treeview 用记录的 `seq` 当行 ID，
   而新引擎的 `seq` 从 1 重新计数。新会话第一条记录就撞上旧行，
   抛出的正是上面那个 TclError——也就是打中 1 的那个异常。
3. **域名窗口的进程列表自我递归。** 刷新函数既重建列表框（触发
   `<<ListboxSelect>>`），又绑在这个事件上。用户点一下进程，
   处理函数立刻把列表重建并把选中项重置——点击等于没点。

**修复**：

1. `_pump` 整体包进 try/except 并把重新排期放进 `finally`。
   它现在**不可能**停止：出错就记一条日志，跳过这一帧继续。
2. 启动新会话时清空上一个会话的记录与域名表（只清成功的启动，
   失败时保留现场）。新引擎编号从头开始，旧行留着就是定时炸弹。
3. 把刷新拆成两个函数：`_refresh_domains_window` 重建进程列表，
   `_refresh_domain_rows` 只重画右侧表格；选中事件只绑后者。
   选中项按**进程名**（而不是索引）跨刷新保持。

**验证**（驱动脚本，两个进程的场景）：

```
[选择测试] 点击第 2 项 -> 选中 'BaiduNetdisk.exe'   右表 1 行，与该进程域名一致: True
[选择测试] 回到第 1 项 -> 'BaiduNetdiskHost.exe'    一致: True
[session 1] 引擎运行时长 7.7s -> 12.7s   界面仍在刷新
[session 2] 引擎运行时长 7.7s -> 12.7s   界面仍在刷新
域名窗口进程列表（session 2）: ['BaiduNetdiskHost.exe  (2)']
```

用**引擎运行时长**而不是记录数做存活判据：目标只在启动时解析一次域名，
健康界面的记录数同样是不动的，用它判断会把正常状态误判成冻结。

**TUI 侧**：同样的导航加了单元测试
`domain_view_navigates_both_panes`——它本来就是对的，
用户遇到的第 3 条只在图形界面存在。

> 教训：一个"打中 1"的异常 + 一个只在末尾排期的循环 = 整个界面静默死亡。
> 自排期的循环必须把排期放进 `finally`。

### 6.14 hosts 写入功能中修掉的两个缺陷

**(1) 结束标记以开始标记为前缀。**

区块标记第一版是：

```text
# === NetMonitor managed entries
# === NetMonitor managed entries end ===
```

后者以前者为**前缀**，所以按前缀查找"开始标记"时会把结束行也匹配上。
正常路径不会出错（找到开始行之后才去找结束行），但一个只剩结束标记的文件
——用户手动删了一行，或上次写入被打断——区块定位就会错，接着可能删掉不该删的内容。

测试 `rewriting_replaces_rather_than_appends` 直接以断言的形式抓住了它
（`text.matches(MARK_BEGIN).count() == 2`）。

修法有两处，都很小但都是必要的：

- 标记改成互不为前缀：`...entries begin ===` 与 `...entries end ===`；
- 区块定位改成**逐行**判断而不是子串查找——标记只有在行首才算标记。
  顺带得到一个更好的性质：结束标记缺失时，区块按"一直到文件末尾"处理，
  这种文件仍然是可修复的，而不是只能报错。

**(2) 并列时选到了最后一个地址。**

`best_ipv6` 原本用 `max_by_key` 按作用域取最大值。Rust 的 `max_by_key`
在多个元素并列最大时返回**最后一个**——也就是说，同一个作用域里有多个地址时，
"最优地址"会选到解析器返回顺序里的**末尾**那条。而那条顺序是有意义的
（服务器偏好，CDN 场景下通常反映就近程度），选末尾正好选反了。

改成显式循环、严格大于才更新，并在注释里写明为什么不能用 `max_by_key`。

两个缺陷都是**单元测试发现的**，不是运行时发现的——这正是给这一段写测试的理由：
它改的是系统文件，出错代价高，而在临时文件上做完整往返测试几乎不花什么成本。

**核心安全属性的测试**：写入再移除之后，文件与原始内容
**SHA256 完全一致**（`write_then_remove_restores_the_file_exactly`），
以及"区块之外的每一个原始行都还在"（`writing_leaves_every_other_byte_alone`）。

### 6.15 自动模式与实时预览（本轮新增）

**需求**：打开自动模式后，特定进程的域名表一变就自动写入 hosts；预览要标注哪些
域名已经写入；预览要跟着域名表自己更新，不再靠按按钮。

**实现要点**：

| 关注点 | 做法 |
|---|---|
| 不抢在 AAAA 之前写 | 该进程的域名**全部查询完毕**才写。否则有 IPv6 的域名会先被写成 `127.0.0.1`，几毫秒后再改回来——中间那一下是错的，而且每次多赔一对备份 |
| 不在突发中反复写 | 计划稳定 `AUTO_DEBOUNCE`（1.5 秒）后才写。一个页面加载会在几百毫秒内加上几十个域名 |
| 判断"要不要写" | 拿**计划**和**文件里实际的区块内容**比，而不是和记住的状态比——手工改过 hosts 之后它能发现并纠正 |
| 只写不删 | 域名表变空时什么都不做。清空区块仍需要明确操作，免得域名表意外清空就抹掉 hosts |
| 备份不无限增长 | 自动模式每次写都备份，超过 50 个自动清理最旧的 |
| 预览实时 | 图形界面在域名表变化后约 1.2 秒内自动刷新（限流，避免几十次往返）；终端界面本来就每帧重算 |

**实测**（两批域名，间隔 10 秒）：

```
第一次自动写入：            第二次自动写入（新增域名的第二次变化）：
  127.0.0.1                wave1-a.invalid    127.0.0.1   wave1-a.invalid
  2606:4700:10::ac42:93f3  www.example.com    127.0.0.1   wave2-b.invalid   ← 新增
                                              127.0.0.1   wave2-c.invalid   ← 新增
                                              2606:4700:10::ac42:93f3  www.example.com  ← 保留
```

关键一条：`www.example.com` 写进去的是**真实 IPv6 地址而不是 127.0.0.1**，
证明它确实等到了 AAAA 答案。自动写入 2 次、备份 2 个、用户原有内容完好。

图形界面同场景：预览行数 **2 → 4，全程未按任何按钮**，
状态列从「未写入」变为「已写入」，状态栏「计划 4 条：已写入 4 条，需要更新 0 条」。

**过程中发现的一个界面缺陷**：图形界面的「或附加到」用的是一次性的 `--attach`，
所以"先开监控、稍后启动程序"这个最自然的顺序在界面里**根本走不通**——
输入名字时进程还不存在，什么都不会被收编，界面看起来像坏了。
命令行早就有了持续监视的 `--watch`，只是没暴露到界面上。
已改为 `--watch` 并更新了标签文字。

> 教训：一个只在命令行存在的能力，等于在界面里不存在。

### 6.16 地址过滤与域名表解析地址（本轮新增）

**需求**：主界面过滤加一个按 IP 地址过滤；域名表里显示该域名当前解析的地址。

**地址过滤**支持三种写法，因为人们实际会输入这三种：

| 输入 | 行为 |
|---|---|
| `20.205.243.166` | 精确匹配 |
| `104.16.0.0/12`、`2606:4700::/32` | 按前缀匹配——CIDN 网段用这个才有意义 |
| `104.16.`、`2606:` | 子串匹配，边打边筛 |

前缀匹配需要**结构化**的地址，所以给 `Record` 加了 `resolved: Vec<IpAddr>`，
而不是去解析已经渲染好的 `detail` 字符串——那等于每次按键都对每一行重新做一遍
文本解析。实测：`104.16.0.0/12` → 1 条、`2606:4700::/32` → 1 条、`2606:` → 1 条、
`192.168.` → 0 条。

**过程发现的一个保真度问题**：一条记录是在**查询被看到**时创建的，它的 DNS 应答
几毫秒后才回来——所以早期那些行本身没有地址，用 IP 过滤会漏掉它们。
修法是让过滤在记录自身没有地址时，回退去查域名表里该域名的最新地址。
图形界面实现为回退到 `self.aaaa[domain]["resolved_ips"]`，O(1) 且总是最新的。

同一轮还修了一个`resolved_ips` 传递断链：引擎已经把它放进 `record` 和 `aaaa` 事件，
但图形界面的事件处理函数没有把它抄进自己的字典，于是域名表那一列一直是空的——
**引擎侧有数据不等于界面侧有数据**。

### 6.17 "很多域名没有解析地址"的成因与修复（用户报告）

**用户报告**：为什么很多域名都查不到当前解析的 IP？

**定位**：设计一个判别实验——先用 `nslookup` 解析、再让被监控程序解析同一个名字。

第一次就发现实验本身错了：**`nslookup` 用的是它自己的解析器，不经过 Windows
DNS 客户端缓存**，所以它根本没预热缓存。改用 `ping`（走系统解析器）之后才复现。

**根因**：命中 Windows DNS 客户端缓存的解析，**仍然会产生 ETW 3006 事件**
（所以域名照样进表），但**不会发出任何数据包**，因此抓不到应答，
关联缓存里也就没有地址。浏览器加载一个页面时大部分子资源都是缓存命中，
所以这个现象非常普遍。

决定性证据（缓存预热后再监控）：

```
缓存预热完成，缓存条目数: 8
record 事件: 2   其中带地址: 0
```

**修复**：程序本来就在为域名表里的每个域名做 AAAA 查询，这次**同时做 A 查询**，
把结果作为"自解析地址"合并进显示。额外的开销通常为零——名字在缓存里时，
这个查询本身就命中缓存、不发包。

**又一层发现**：修好之后测试里 `由本程序解析` 一直是 `False`，地址却有了。
原因是我们自己发出的 A 查询，**它的应答又被抓包源捕获**，于是先填进了观察缓存。
两条路径殊途同归——真正解决问题的是"多发一个 A 查询"，自解析字段是兜底。
兜底并非多余：关掉抓包（`--no-npcap`）时它是唯一来源，实测：

```
github.com        ['20.205.243.166']                    由本程序解析=True
www.example.com   ['172.66.147.243', '104.20.23.154']   由本程序解析=True
```

而修复后的最终效果（缓存命中 + 只有 A 记录的域名，正是之前为空的情形）：

```
github.com       record 带地址 0 条   域名表 20.205.243.166
www.bing.com     record 带地址 0 条   域名表 202.89.233.101, 202.89.233.100
```

**记录行 vs 域名表**：记录行里的地址是"该行创建那一刻已知的地址"，所以缓存命中
的那一行会一直是空的；域名表里的是持续更新的当前值。用地址过滤时，记录行自身
没有地址会回退到域名表，所以过滤不会因此漏行。

### 6.18 "hosts 文件会自动还原"——空计划写入会清空整个区块（用户报告）

**用户报告**：每次关闭程序重启后，hosts 文件总是会自动还原；还原和删除应该由用户执行。

**排查**：先按"有代码在自动还原"去找，把三样都排除了——

- 列出所有会改动 hosts 的调用点：全部挂在用户操作或自动模式后面；
- headless 路径实测"写入 → 关闭 → 重启（不下任何命令）"：**文件字节不变**；
- 图形界面同样流程实测：**文件字节不变**。

**真因**是在测"重启后立刻按写入"时找到的：重启后域名表还没填上，
此时点「写入」，程序会渲染一个**空的**托管区块盖在原有区块上，把之前写入的条目
全部删掉。提示只写"已写入 0 条"，完全看不出发生了删除。

```
写入前条目: ['2606:4700:10::6814:179a  www.example.com  # nm']
引擎回复  : 已为 NeverRuns.exe 写入 0 条 IPv6 记录、0 条 127.0.0.1 拦截记录
写入后条目: []
原有条目是否还在: False
```

"重启后打开 hosts 窗口 → 按写入"正是最自然的操作顺序，所以每次重启都会命中。
用户看到的"自动还原"，实际是自己的写入动作触发的。

**修复**：写入和清除分成两件事。

- **空计划写入被拒绝**，并说明"继续写入会清空已有的 N 条记录"；
- 清除走专门的「移除本程序的条目」，有独立确认；
- 回归测试 `an_empty_write_is_refused_rather_than_erasing` 断言拒绝发生且文件字节不变。

**顺带收紧的两处"程序自己动手"**（用户的诉求是"还原和删除由用户执行"）：

1. **自动模式不再清理旧备份**。按数量自动删除，第一个删掉的就是最旧的那份——
   而最旧的那份往往正是出事时最需要的。清理改成显式操作（终端 `D`、图形「清理旧备份…」），
   测试 `backups_are_only_removed_when_the_user_asks` 断言"打开窗口、读取视图"都不会删文件。
2. **终端界面 `L` 恢复备份加了确认**。它原来是**一次按键直接覆盖文件**、没有任何确认，
   而且 `L` 就在其它按键旁边——这是最容易误触的路径。

### 6.19 把"是否管理员"当作"能否抓包"的判据是错的

**测量**：在令牌**未提升**的进程里运行 `netmon --doctor`，输出
`elevated : NO`，但紧接着 `etw session : OK`，并且实际抓包完全正常——
`Microsoft-Windows-DNS-Client` 订阅成功，记录正常输出。

**影响**：图形界面原本在启动时调用 `IsUserAnAdmin()`，判定失败就弹 UAC 询问。
在这个环境下这纯属打扰，更糟的是——接受提权会关掉**本来工作正常**的会话。
测试驱动脚本正是因此被销毁，暴露了这个设计问题。

**修复**：删掉启动时的权限询问。改为启动之后看引擎**实际报告**的结果
（`status` 事件里的 `etw` / `npcap` 两个布尔值，是引擎根据自己有没有成功订阅
提供程序得出的），只有数据源真的没起来才提示，并在告警条上给一个
「以管理员身份重启」按钮。同理，`scriptserify.ps1` 里原来那条
"running elevated" 断言改成了断言真正要验证的东西：
`netmon --doctor` 能否开出 ETW 会话。提升与否只作为信息打印。

> 一般性教训：**断言能力本身，不要断言能力的代理指标。**

### 6.20 强制结束进程会让 ETW 永久失效（严重）

**症状**：工具启动后列表一直是空的，或者只有零星几条，没有任何报错提示。

**定位过程**：

1. 反复强制结束（`taskkill /F`）NetMonitor，发现从第二次起 ETW 就开始报
   `EnableTraceEx2` / `StartTraceW` 返回 **1450（系统资源不足）**；
2. `logman query -ets` 显示系统里堆着 4 个 `NetMonitor-<pid>` 会话——
   它们的属主进程早就没了；
3. 逐条 `logman stop` 清掉后，ETW 立刻恢复正常；
4. 连续 5 次强杀可稳定复现。

**根因**：普通（非私有）ETW 实时会话的寿命**长于**创建它的进程。
`TerminateProcess` 不会停止会话，它会留在系统里继续占用内核 ETW 资源。
积累到一定程度后，新建会话或启用提供程序就返回 1450。

此时主数据源（ETW）已死，只剩抓包源；而抓包源看到的 DNS 包属主是 `svchost.exe`，
按设计被抑制（§9.1），结果是**目标应用的查询一条都看不到，且没有任何显式错误**。

**尝试过但被否决的方案**：`EVENT_TRACE_PRIVATE_LOGGER_MODE` 是官方推荐的解法
（会话随进程销毁）。实测在本机 **不可用**——`StartTraceW` 对该模式的每一种组合
（单独、配 `EVENT_TRACE_PRIVATE_IN_PROC`、配显式会话 GUID）都返回
`ERROR_INVALID_PARAMETER`(87)。该测量保留为
`win::etw::tests::probe_accepted_logfile_modes`，供未来 Windows 版本复核。

**最终方案**（三层，都已实测）：

| 层 | 做法 | 效果 |
|---|---|---|
| 启动清扫 | 枚举所有 `NetMonitor*` 会话，**只停掉属主进程已消失的** | 不误伤并行运行的第二个实例；实测 5 次强杀后残留稳定为 1 且每次启动清零 |
| 失败重试 | 撞上 1450 时清扫一次再重试 | 覆盖清扫与建会话之间的竞态 |
| 手动兜底 | `netmon.exe --clean-sessions` | 强制停掉全部，含属主仍存活的 |

**过程中修掉的两个次级缺陷**：

- `QueryAllTracesW` 要求调用者预先填好每个 `EVENT_TRACE_PROPERTIES` 的
  `Wnode.BufferSize`。漏填不会报错，只是"什么会话都查不到"——第一版清扫因此
  静默失效。
- 清扫最初只认 `NetMonitor-<pid>`，而图形界面用了 `NetMonitorGUI-<pid>`，
  于是 GUI 的残留会话完全不在清扫范围内。改为按**最后一段数字**解析后覆盖。

**回归测试**：连续 5 次 `taskkill /F`，每次启动自动清掉上一条残留；
第 5 次之后 ETW 仍正常，记录正常输出。修复前第 2 次起即永久失效。

### 6.22 写入改成追加式合并，按进程独立（承接 6.18，用户要求）

**用户要求**：hosts 的写入和删除都要**按进程独立**，且都要用户来执行（自动模式除外）；
写入时已写过的域名跳过（原来因无 IPv6 而写成 `127.0.0.1` 的，现在有 IPv6 了要改过来），
没写过的追加，**不动已经写入的内容**。

**6.18 的修法是"拒绝空写入"，那只是挡住了那一次误删。** 结构上的问题还在：
写入仍然是"用这次的计划整个替换托管区块"，所以——

- 写进程 A，再写进程 B → A 的条目被顶掉（B 的计划里没有 A 的域名）；
- 移除是"移除整个区块"，删 A 会连 B 的一起删。

对用户来说这两件事都表现为"我操作一个进程，另一个进程被殃及"，
而"按进程独立"正是这次要的。

**改法**：`render_with`（整块替换）换成 `merge`（把一份计划并进区块）。
合并函数里**没有删除这个动作**——它只会追加新行、把 `127.0.0.1` 升级成 IPv6 地址、
以及在已存在的行上登记本进程。删除只有 `unclaim` 会做，且必须点名进程。

每条记录末尾带上写入它的进程：`# nm msedge.exe,baidunetdisk.exe`。
共用一行（两个进程都解析同一个域名）时只写一行，双方的名字都记上；
移除其中一个只去掉它的名字，行留着——否则先移除的那个进程会把另一个还在用的
域名一起带走。

预览表相应拆成两列：「hosts 里的现状」（未写入 / 已写入 / 已写入(其它进程) /
已写入(127.0.0.1) / 已写入(地址不同) / 文件里已有(非本程序)）与
「本次写入」（追加 / 更新为 IPv6 / 登记本进程 / 不动 / 跳过）。
两列出自同一个判定函数，`merge` 用的就是它，所以预览不会承诺一件写入不做的事。

**测试**（`cargo test` 单元 + 三个端到端驱动）：

| 断言 | 结果 |
|---|---|
| 单元测试 | **137 / 137**（新增 14 项：合并、升级、共用行、按进程移除、逐字节保留、标记解析、终端界面渲染） |
| 写 A 再写 B：A 的行逐字节不变，B 追加，共 3 行无重复 | 通过 |
| 重复写 A：`unchanged=true`、无备份、文件字节不变 | 通过 |
| 共用域名只写一行，标记为 `# nm A,B` | 通过 |
| 移除 B：删独占 1 行、共用 2 行保留、文件里不再有 B 的名字 | 通过 |
| 移除 A：文件恢复到最初内容（**逐字节**） | 通过 |
| 移除从未写入的进程：`unchanged=true`，文件不动 | 通过 |
| 无 IPv6 → `127.0.0.1`，随后有 IPv6 → 原地更新（不新增行） | 通过 |
| 已有的 IPv6 地址不会被反向降级成 `127.0.0.1` | 通过 |
| 用户在文件里自己写的行：跳过，不追加第二行 | 通过 |
| 自动模式：20 秒内只写 1 次、1 个备份，稳定后不再重写 | 通过 |
| GUI：表格出现「本次写入」列、两个移除按钮、按操作分类的计数 | 通过（注入事件驱动渲染，不开窗口） |
| 终端界面：hosts 视图列出按进程分布、两个移除键位 | 通过（`hosts_view_shows_per_process_state_and_both_removals`） |

期间由终端界面渲染测试发现并修掉一处统计口径问题：**共用行只算在第一个进程名下**，
于是 b.exe 在"按进程"里根本不出现——一个进程明明依赖某一行，界面却说它什么都没有。
改为**每个拥有者各计一条**（共用行会重复计入，这正是"这行我也要"的意思）。

自动模式里那个"要不要写"的判断同时修了一处会退化的地方：原来拿**整份区块**和
**单个进程的计划**比，区块里一旦有别的进程的条目就永远判为"有变化"，会每 1.5 秒
重写一次、每次都留一个备份。现在改成"把计划并进去，看结果和现在是否一样"。

### 6.23 域名表与 hosts 更改记录的本地缓存（用户要求）

**用户要求**：域名表和 hosts 更改记录应该有本地缓存，每次启动保留先前的记录，
以便管理先前写入的 hosts。

**为什么这不是"锦上添花"**：hosts 条目比产生它的会话活得久。重启后域名表是空的，
于是

- 看不到那些条目是谁写的、当时解析到什么；
- 界面里**选不中**那个进程，因为它不在域名表里——只剩「移除全部」一条路，
  而按进程移除正是上一轮刚做的功能。

**改法**：两个文件，默认放在可执行文件旁的 `netmon-data\`（`--data-dir` 可改，
`--no-cache` 可关）。

| 文件 | 写法 | 读法 |
|---|---|---|
| `domain-tables.json` | 每 30 秒一次 + 退出时，**原子替换** | 启动时载入，标记为 `archived` |
| `hosts-history.ndjson` | 只追加，一行一条 | 读时跳过坏行，取最新 N 条 |

几个刻意的决定：

1. **缓存只用于"看"和"管"，不用于"写"**。自动模式规划时过滤掉 `archived` 行——
   把上次的地址写回去等于断言一个没人验证过的事实。手动写入不受限（那是你点名的）。
2. **hosts 窗口的进程列表 = 当前会话的域名表 ∪ hosts 文件里出现的进程名**。
   后者是"程序已经不在了但条目还在"的唯一线索，缺了它按进程移除就没法用。
3. **按进程移除在重启后照常工作**，因为归属信息本来就在文件里（`# nm a.exe`），
   不依赖内存状态。
4. **90 天保留期，但 hosts 文件里还有条目的域名永久保留**——缓存的意义就是管它们。
5. **重新打包时保留 `netmon-data\`，但不放进 zip**：里面是用户访问过的域名。

**过程中发现的一个真实缺陷**：崩溃会把最后一行日志截断（没有换行符），下一次
追加会把新记录**粘在残行后面**，两条一起变成坏行。修复是追加前检查文件末字节，
不是换行就先补一个；回归测试 `a_truncated_history_line_does_not_hide_the_rest`
构造了这个场景（有效 → 残行 → 有效，断言读回 2 条而不是 1 条）。

**验证**：

| 项目 | 结果 |
|---|---|
| 单元测试 | **149 / 149**（新增 14 项：快照往返、坏文件忽略、历史顺序与上限、坏行跳过、恢复为 archived、实时观测解除 archived、不覆盖本会话数据、缓存往返、自动模式忽略缓存行、历史界面渲染） |
| 端到端（`persist1.py`，三次启动） | 全部通过 |
| 第 1 次运行：抓取 → 写两个进程 → 停止，两个缓存文件落盘 | 通过 |
| 第 2 次运行（目标没在跑）：启动即列出上次的进程，行标 `archived`，地址保留 | 通过 |
| 第 2 次运行：预览全部为「不动」且标「上次会话」，不需要重新解析 | 通过 |
| 第 2 次运行：更改记录能看到第 1 次的两次写入（含时间与条数） | 通过 |
| 第 2 次运行：按子进程移除 → 删 1 行、共用 2 行保留、主进程条目不动 | 通过 |

| GUI：只出现在 hosts 文件里的进程进入下拉列表；预览与域名表标出「上次会话」；历史标签页列出记录并按动作着色 | 通过（注入事件驱动渲染） |

### 9.1 hosts 分进程行为的复现

```bash
# 1. 单元测试（含合并 / 归属 / 按进程删除的回归）

# 2. 两个进程各写各的：追加、跳过已写入、共用行、按进程删除
python -I .cache/test/perproc2.py .cache/target/release/netmon.exe

# 3. 预览与 hosts_read 的字段（GUI 画表用的就是这些）
```
